## Highlights

- Cluster API is now using Golang 1.26, CR v0.25, CT v0.23

- Graduations:
  - PriorityQueue and ReconcilerRateLimiting feature gates to GA (#14079)
  - ClusterTopology to beta and enabled per default (#14398)
  - MachineTaintPropagation feature gate to beta and enabled per default (#14395)

- Improvements to in-place updates 
  - CanUpdateMachine and CanUpdateMachineSet extension can set a new field in the response to inform CAPI when an update affects availability,
    thus allowing extension authors to avoid creating a spare VM when it is considered safe (#14200, #14195)
  - CanUpdateMachine and CanUpdateMachineSet extension can return allowedOperations, allowing extension authors to define constraints for how the rollout can be performed by CAPI (#14367, #14378)
  - CanUpdateMachine and CanUpdateMachineSet extension can return RetryAfterSeconds, thus supporting decisions taking a long time (#14350, #14378)
  - UpdateMachine extension can now return a detailed updateStatus, thus surfacing in CAPI more details about the update progress (#14385)
  
- Support for in-place updates for clusters with a single control plane machine (by combining the features above)

- MachineHealthCheck improvements
  - MHC now supports CEL-based health check rules, thus allowing CAPI users to express more sophisticated health checking rules (#14297)

- ClusterClass improvements
  - Support for ClusterClass without template objects (#14092)

- KCP remediation improvements
  - Improved matching between etcd member to machine being deleted by KCP and avoid deleting learners after Node registration
    both extending the number of race conditions that can be automatically detected and managed by CAPI (#14258, #14199)
  - Improved management of remediation retries, providing a stronger foundation for dealing with Machine issues.
    - KCP should not remediate machines unhealthy since before MinHealthyPeriod expires (#14331)
    - Reset MaxRetry and the remediation sequence when the KCP spec changes (#14369)
    - Reset MaxRetry and the remediation sequence when starting in-place update (#14458)

- MachineDeployment improvements 
  - Fix max-surge check-in rollout-planner (#13983)
  - Handle rollout edge cases (#14312)
  - Improve rollout planner code & test (#14201, #14226, #14260)

- Performance at scale and reduce memory footprint
  - Introduce DynamicCache to reduce static memory allocation for unstructured objects (#13803)
    - CAPI -50%, KCP -37% for 1K clusters, 27K machines
  - Optimize memory usage for conversion and ssa.Patch (#14075, #14085)

- Logging improvements 
  - Add Log rate limiting to reduce log noise (#14422)
  - Also #14413, #14445, #14420, #14425, #14438, #14257

- Book improvements
  - A long due reshuffle/refresh of the Cluster API documentation, with a cleaner a simpler split between user guide (the documentation
    for CAPI users), and the developer guide (the documentation for contributors/providers/extension authors).

- New providers 
  - cluster-api-provider-exoscale (#14306)
  - cluster-api-provider-kairos (#14045)
  - cluster-api-provider-kairos-fleet (#14046)

## Deprecation Warning

Important:

- The v1beta1 API version in core Cluster API, CABPK and KCP is on track to be unserved in CAPI v1.16. All the consumers of this API version should migrate to v1beta2 ASAP.
  - Utils for the Cluster API v1beta1 condition types (condition helpers, patch helper etc.) will be removed as a next step.
  - All the status.deprecated fields existing in v1beta2 types (used for v1beta1 down conversions) types will be removed as a next step.
- Support for the Cluster API v1beta1 contract versions is on track to be dropped in CAPI v1.16. Provider should start implementing the v1beta2 contract ASAP.

For additional details for providers, please take a look at [Cluster API v1.15 compared to v1.14](https://main.cluster-api.sigs.k8s.io/developer/providers/migrations/v1.14-to-v1.15.html).

```sh
ETCD_VER=v3.7.4

# choose either URL

rm -f /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz

tar xzvf /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz -C /tmp/etcd-download-test --strip-components=1 --no-same-owner
rm -f /tmp/etcd-${ETCD_VER}-linux-amd64.tar.gz

/tmp/etcd-download-test/etcd --version
/tmp/etcd-download-test/etcdctl version
/tmp/etcd-download-test/etcdutl version

# start a local etcd server
/tmp/etcd-download-test/etcd

# write,read to etcd
/tmp/etcd-download-test/etcdctl --endpoints=localhost:2379 put foo bar
/tmp/etcd-download-test/etcdctl --endpoints=localhost:2379 get foo
```

###### Docker

etcd uses [`gcr.io/etcd-development/etcd`](https://gcr.io/etcd-development/etcd) as a primary container registry, and [`quay.io/coreos/etcd`](https://quay.io/coreos/etcd) as secondary.

```sh
ETCD_VER=v3.7.4

rm -rf /tmp/etcd-data.tmp && mkdir -p /tmp/etcd-data.tmp && \
  docker rmi gcr.io/etcd-development/etcd:${ETCD_VER} || true && \
  docker run \
  -p 2379:2379 \
  -p 2380:2380 \
  --mount type=bind,source=/tmp/etcd-data.tmp,destination=/etcd-data \
  --name etcd-gcr-${ETCD_VER} \
  gcr.io/etcd-development/etcd:${ETCD_VER} \
  /usr/local/bin/etcd \
  --name s1 \
  --data-dir /etcd-data \
  --listen-client-urls http://0.0.0.0:2379 \
  --advertise-client-urls http://0.0.0.0:2379 \
  --listen-peer-urls http://0.0.0.0:2380 \
  --initial-advertise-peer-urls http://0.0.0.0:2380 \
  --initial-cluster s1=http://0.0.0.0:2380 \
  --initial-cluster-token tkn \
  --initial-cluster-state new \
  --log-level info \
  --logger zap \
  --log-outputs stderr

docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcd --version
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl version
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdutl version
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl endpoint health
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl put foo bar
docker exec etcd-gcr-${ETCD_VER} /usr/local/bin/etcdctl get foo
```
